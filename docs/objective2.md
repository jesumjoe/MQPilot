# Objective 2: Multi-Plane Detection Engine

## Architecture

The detection engine combines two planes of analysis for MQTT traffic, sitting inside the `edge_sensor` container:

1. **NFQUEUE**: Uses iptables to intercept MQTT traffic (port 1883) and forward it to queue 1.
2. **Suricata IPS**: Listens to NFQUEUE 1, applies custom signature rules, and logs telemetry/alerts as EVE JSON.
3. **EVE JSON**: The primary machine-readable telemetry interface produced by Suricata.
4. **Feature Extractor**: A Python component that reads EVE JSON and aggregates behavioral observations over a rolling 10-second window.
5. **Isolation Forest**: A machine learning model trained purely on baseline traffic to detect anomalies in the extracted behavioral feature vector.
6. **Fusion Engine**: Correlates the output from both planes (Suricata alerts + ML anomalies) and generates unified security events.

## Request/Data Flow

```text
MQTT traffic
    ↓
Suricata (via NFQUEUE)
    ↓
EVE telemetry (eve.json)
    ↓
feature extraction (Python)
    ↓
Isolation Forest (ML inference)
    ↓
fusion (Decision Engine)
    ↓
security decision (NORMAL, SIGNATURE_THREAT, BEHAVIORAL_ANOMALY, CORRELATED_THREAT)
```

## Signature Plane

* **Suricata Role**: Provides inline deep packet inspection and signature-based detection/prevention.
* **Custom Rules**: Managed in `edge_sensor/rules/mqpilot.rules`, targeting specific protocol abuse, payloads (e.g. `C2_BEACON`), and bruteforce attempts.
* **IPS Behavior**: Suricata can actively `DROP` traffic matching specific rules (like known C2 signatures).
* **EVE Alerts**: Generates standard JSON alerts that feed into the fusion engine.

## Behavioral Plane

* **Baseline Collection**: Normal behavior is generated by `traffic_gen/generate_baseline.py` and extracted into feature vectors.
* **Features**: Metrics include `packet_count`, `byte_count`, `packets_per_second`, `publish_count`, `unique_topics`, etc.
* **Windowing**: A 10-second aggregation window is used.
* **Isolation Forest**: Unsupervised ML model trained on the baseline data.
* **Anomaly Score / Threshold**: The model returns a negative score for anomalies. A threshold (default `0.0`) is used to flag outliers.

## Fusion Plane

The engine synthesizes the results into one of four states:
1. **NORMAL**: No Suricata alert, no ML anomaly.
2. **SIGNATURE_THREAT**: Suricata alert triggered, but behavior remains within normal ML bounds.
3. **BEHAVIORAL_ANOMALY**: ML detects unusual traffic patterns, but no known signature is matched.
4. **CORRELATED_THREAT**: Both a signature is triggered and behavioral anomaly is detected.

## Training Procedure

1. Run the system under normal baseline conditions (`generate_baseline.py`).
2. Run the `feature_extractor` on the resulting EVE JSON to populate `baseline_features.csv`.
3. Execute `python -m detector.train_model` which trains the `IsolationForest` on the CSV and saves the model to `models/isolation_forest.joblib`. (If data is missing, it falls back to generating synthetic normal data to prevent crashing).

## Testing

Simulate attacks using `generate_attack.py`:
* `python generate_attack.py rate`: Triggers behavioral anomaly (excessive publishes).
* `python generate_attack.py signature`: Triggers signature threat (C2 payload).
* `python generate_attack.py correlated`: Triggers both simultaneously.
* `python generate_attack.py topic`: Triggers behavioral anomaly (excessive unique topics).

## Limitations

* **Unsupervised ML does not identify the exact attack type**: It only flags deviations from the baseline.
* **Baseline quality affects model quality**: If the baseline contains attack traffic or is too narrow, the model will be inaccurate.
* **Behavioral thresholds affect false positives**: A strict threshold increases false positives.
* **Model drift is possible**: The model needs retraining if normal IoT behavior changes.
* **Timing mismatch**: Suricata operates on per-packet speed, whereas the ML operates on a 10-second window, so correlated events are grouped by the window timeframe.
